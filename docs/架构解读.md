# PlantOmics Hub 架构解读（v2.3 · 2026-11-01）

> 这份文档不是规则、不是进度，是**给人读的解释**：为什么这样分层、一次请求实际经过哪些代码、哪些地方是刻意的取舍。
> 规则以 `AGENTS.md` 为准；工具清单以 `README.md` 为准；本文只解释"为什么"和"在哪"。
> 每个结论都带代码定位；**定位不写在括号里就不算**，因为行号会漂，读者要能自己核。

---

## 一、一句话定位

这套东西不是"把几个数据库的 API 聚合起来"，而是：**把别人的公开接口，做成模型能可靠调用、失败能讲清、结论能复现的工具。**

差别在"可靠"这三个字。同一个上游，模型直接 fetch 会踩的坑是：不知道有哪些端点、参数传错被静默忽略、返回 600 KB 塞爆上下文、查无与出错长得一样、出问题说不清查的是哪次。本仓的每一层基本都是在堵这些坑。

---

## 二、五层结构，每层只解决一件事

```
使用端   Claude Code / Codex / Reasonix / DeepSeek Harness
  ↓
出口层   src/mcp（stdio）· src/dsh（宿主插件）· src/service（HTTP 服务）
  ↓
编排层   src/core/invoke.ts —— 工具调用的唯一入口
  ↓
注册层   src/core/registry.ts —— 启动时硬校验，不合格直接崩
  ↓
适配层   src/sources/<id>/ —— 一源一目录：manifest + tools + fixtures
```

外加两条横切：**检索层** `src/retrieval/`（帮人选源）与**输出排版** `src/core/format.ts`（把上游 JSON 变成有界、带出处的文本）。

**为什么这么切**：一个源坏了只影响 `src/sources/<id>/`，不会拖垮注册表；一份工具定义同时服务三个出口（`src/core/invoke.ts` 的注释说明了原因——两个出口各写一遍会导致入参校验、取消信号、错误文案三处不一致）。

## 三、一次 `tools/list` 走了什么

1. 进程启动 → `src/service/cli.ts` 读环境变量（`src/service/config.ts`），装配注册表
2. **预算门禁**：`src/service/http.ts:276` 调 `assertBudget`（`src/service/budget.ts`）。它此刻只做两件事：**工具名长度是否会被宿主截断**、**默认集是否超过软建议**（超了只警示）。**全库源数与工具数不拦截**——这是 v2.3 与旧版最大的区别
3. 连接进来 → `POST /mcp`，鉴权在 `src/service/http.ts:409`（`Authorization: Bearer`，缺头即 401，**在读取请求体之前就拒绝**）
4. **按请求选源**：`src/service/subset.ts:28` 读 `x-plantomics-sources`。这是"这次要装哪些源"，不是权限——不带这个头就拿到服务端全集
5. 子集预算：`src/service/budget.ts:120` `assertSubsetBudget` —— **超过 80 个工具就 400**，这是整个系统唯一的硬阈值
6. 返回 `tools/list`。元工具 `hub_find_sources` / `hub_status` 跟着子集一起下发（`src/retrieval/index.ts`）

## 四、一次 `tools/call` 走了什么

所有出口都过 `src/core/invoke.ts`（唯一入口），顺序是：

```
tools/call
  → 参数校验（additionalProperties 不许乱传，传错名字会报错而不是静默忽略）
  → 适配器发起请求（src/core/http.ts：UA / 超时 / 有界重试）
  → 上游返回 JSON 或 4xx/5xx
  → 错误分类（合法空结果 / 上游业务错误 / 结构漂移 / 网络失败，四类不许混）
  → 排版（src/core/format.ts，DEFAULT_MAX_BYTES = 4096 字节，`format.ts:11`）
  → 附录出处尾注（源 / 完整请求含参数 / HTTP 状态 / 耗时 / 查询时刻）
  → ToolResult { text, raw }（raw 不进模型上下文）
```

两个容易忽略的细节：

- **预算按 UTF-8 字节算，不按字符**。中文一个字 3 字节，按 `text.length` 算会实际撑到 12 KB。
- **出处尾注不许被截断**。截断由 `format.ts` 统一执行，尾注在裁剪之外——因为"这条数据从哪来"比"看到多少行"重要。

## 五、源市场制（v2.3）：三个数字，三种动作，不能合并成"超限拒绝"

| 数字 | 管什么 | 超了会怎样 | 代码 |
|---|---|---|---|
| 全库源数 / 工具数 | 库房里有多少 | **什么都不发生**，只统计 | 无拦截逻辑（旧的 `MAX_SOURCES/MAX_TOOLS` 已降为历史别名，不参与判断） |
| 默认推荐集 40 | 不选源时给你装多少 | **只警示**，照常下发 | `src/service/budget.ts:24` |
| 单次订阅集 80 | 这一次请求装多少 | **服务端 400 拒绝** | `src/service/budget.ts:22` / `:120` |

**为什么市场需要 `GET /catalog`**（`src/service/http.ts:354`、构造在 `src/service/catalog.ts:78`）：页面要算"选中的源 → 工具总数 → 超 40 警示 / 超 80 拒绝"，算错就是给用户装了个调不动的集合。构建快照会漂，所以数据必须**由运行中注册表实时生成**。唯一的数字来源在 `budget.ts`，catalog 不许自己写一遍 80/40。

一个反直觉但重要的口径：**选了 2 个源的 4 个工具，实际下发 6 个**——`hub_find_sources`、`hub_status` 两个元工具会跟着进来，计入预算。页面不算它们，token 就少算三分之一。

## 六、四个刻意的取舍（以及被否掉的另一条路）

1. **薄插件，不内置工具**。插件只负责把服务注册进宿主，工具清单由服务端 `tools/list` 决定。→ 加源只更新服务端，用户零操作。否掉的是"工具打包进插件"：那样每加一个源都要用户升级插件。
2. **不做万能执行器** `hub_call(tool, args)`。→ 它会绕过工具预算、丢掉参数 schema。否掉它的代价是工具数变多，但这是可接受的。
3. **不做数据镜像**。→ 只做调用，不落数据集。`downloads` 这类 35 GB 文件下载倾向永久不接。
4. **检索层放在模型调用之前**，而不是让模型自己从几十个工具里挑。→ 现在是"帮用户选装哪几个源"，把选择成本从每次对话挪到一次配置。

## 六点五、加一个源要过几道关（v2.3 实际流程）

不是"写完 tools 就算接上"。顺序是固定的，跳一步就会在审查或市场暴露：

1. **实测定级**（T1/T2/T3）——至少两个候选端点，SPA 要能从 bundle 里找到 API base，找不到按 T3 只登记不实现
2. **契约起草**：参数、输出、错误四分类（合法空 / 上游业务错 / 结构漂移 / 网络失败）、覆盖范围与盲区
3. **契约独立审查**——不通过就不进实现（STRING 就在这里被拦住过一次，三条 P1）
4. **实现**：`src/sources/<id>/` 下 manifest + tools + 裁剪脱敏的 fixtures
5. **fixtures 证据层级**：声称有原体哈希就必须真有 `rawBody` 且哈希对得上——把"声明"当"证据"是这轮唯一踩到的红
6. **离线测试 + 真实 probe**：`npm test` 全离线，可达性只归 `npm run probe`
7. **实现独立审查**：独立复跑关键断言，反例优先
8. **接线**：`src/sources/index.ts` 一行；**工具数只从 `registry.listTools()` 取，不许数文件**（WheatOmics 有 3 个实现文件，数文件会少报 2 个）
9. **市场可见**：`/catalog` 由运行中注册表实时生成，全库只统计不拦截；用户按订阅集装（≤80 硬，默认 ≤40 软）

> 第 8 步那个坑是真实踩过的：按 `tools.ts` 里的 `const` 数，得到"wheatomics 9 工具、全库 35"，两个都错；而少报的数看起来完全合理，这才是它危险的地方。

## 七、不能声称什么（这些边界必须跟着图一起用）

- 服务是**无状态**的：每条请求独立新建 transport。所以"按请求选源"不是权限隔离，不带头的下一条请求照样拿到全集。
- **没有吞吐与可用性证据**，没测多租户。
- 可达性由 `npm run probe` 单独测，**`npm test` 里没有任何真实网络请求**——这是刻意的，联网测试红了三次之后人就会 `--skip`。
- 一个源查不到 ≠ 不存在。工具描述里的覆盖范围才是结论边界。
- 线上能否调用属另一层证据：离线检查、真实上游 probe、真实 MCP 会话、远端发布，**四层分别说明，不许混称**。
