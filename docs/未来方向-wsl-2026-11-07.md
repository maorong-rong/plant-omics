## ② 方向总述：分四段，按交付物切

**四段交付物**：

| 段 | 交付物 | 一句话目标 |
|---|---|---|
| P0 证据链 | CI 工作流 + 定时探活 + 自动生成的现状报告 | 让“构建过不过、10 源通不通、三通道版本一致不一致”每天由机器回答，而不是靠人临时跑 |
| P1 契约单一真相 | 契约闸 + 统一的默认集 / 计数 / 版本文案 | 同一事实只在一个地方定义，模型、文档、页面、日志读到同一个数 |
| P2 三通道装机闭环 | 一个发布版本 + 干净环境安装证据 | npm、DSH 市场、云服务都指向同一版；新用户按文档能装到并调通 |
| P3 稳定性与覆盖 | 工具级实测报告 + 降级策略 | 39 个源工具都有“实测过 / 明确未验”的状态；上游抖动时有可预期的失败方式 |

**为什么这么切**：

1. **按交付物切，而不是按技术层切。** 每一段结束时都有一件可验收的产物（工作流 / 契约闸 / 发布包 / 覆盖报告），可以单独填进里程碑表、单独派活、单独回滚；不按“前端 / 后端 / 测试”切，避免每段都只完成一半。
2. **P0 必须最先做。** 当前 `npm run check` 本身很强（1196 个离线用例），但它只在本地跑；`.github/workflows/` 没有 PR 检查，合并前靠人记得跑。没有 P0，后面任何契约修改都没有自动闸门，回归只能靠人发现。探活也全靠人手动跑：ensemblplants 昨天 125 秒、今天 31.4 秒，没有历史就无法判断“变好了还是只是这次运气好”。
3. **P1 排在 P2 之前。** 装机失败的直接原因多数是版本 / 计数 / 默认集说法不一致，而不是打包技术本身：市场停在 0.1.0、源码仍是 0.1.1、`doctor` 查旧包名、`hub_status` 报 41 而 `catalog` 报 35。先把“同一事实一个来源”做掉，P2 的发布才有可核对的基线。
4. **P2 必须是一次真实发布，不是“改文档”。** 当前三条安装通道拿到三种东西（npm 0.1.1 / 市场 0.1.0 / 云服务 0.1.1+svc），且源码比 tag 多 8 个提交。只有真的升版本、发一次、三处对齐，才算完成；只改 README 数字会制造第四种说法。
5. **P3 放最后，但不是“可做可不做”。** 39 个源工具里只有 9 个有本次联网证据；30 个只有 fixture 回放。这个缺口不会因为发布一次就消失，且全量实测最贵、最容易被上游限流与抖动拖垮，所以放在前三段把证据链、契约、发布都稳定之后再做。ensemblplants 的降级处理可以提前在 P0 的探活报告里暴露，但“怎么降级”的代码与阈值放在 P3。

**与既有线索的差异**：四段的顺序保留，但边界按实测收窄——P0 的重点从“有日志”改为“有自动闸门与连续历史”；P1 把默认集选择提前到本段，因为三处读数不一致已经直接影响模型；P2 明确是“一次真实发布”，不是改文档；P3 只承诺“失败可分类、覆盖可核验”，不承诺所有上游永不失败。没有新增“扩源”阶段，理由见下。

**这一段明确不做的事**：

- **不新增源。** 现有 39 个源工具仍有 30 个没有联网实测；先加源会把未验证面积继续扩大，也会让计数与默认集的漂移更难收敛。
- **不做检索层“按需展开”。** README 已写明当前 `hub_find_sources` / `hub_status` 只是发现入口，不是按需装工具；这是独立设计，不与本次四段混在一起。
- **不改 UI 版式。** 侧边栏面板是构建期静态清单，真实宿主渲染未验收；先解决“装得上、数一致”，再谈展示。

## ⑤ 需要本涛决定的（3 条，每条两个选项）

### D1. 默认集到底发多少工具：35 还是 41？

**背景**：`src/service/budget.ts` 的 `DEFAULT_SET_SOURCES` 已列出 7 个源，`catalog` / `stats` 按它算出 35；但实际 `tools/list` 与 `hub_status` 仍是 41。当前状态是“目录与统计按 35 算，实际下发与 `hub_status` 自述按 41 算”，三处读数不同。

- **选项 A（真过滤，默认 35）**：默认会话只下发 `DEFAULT_SET_SOURCES` 的 7 个源 + 2 个元工具 = 35；`scod` / `string` / `uniprot` 由用户按需订阅。代价：对现有用户是破坏性变更（工具“消失”），需要按 0.2.0 处理并写迁移说明。
- **选项 B（撤回默认集变更，默认 41）**：默认仍下发全库 41；`catalog` / `hub_status` / README 统一改成 41，软建议 40 只做提示。代价：32K 上下文更拥挤，软建议会长期报警；但无破坏性变更，可走 0.1.2 补丁线。

### D2. 发布线怎么走：先 0.1.2 还是直接 0.2.0？

**背景**：`v0.1.1` tag 已指向 `6437d98`，`main` 比它多 8 个提交但 `package.json` 仍是 0.1.1，因此当前 `main` 不能按 0.1.1 再发；市场又停在 0.1.0。CHANGELOG 已有一段“0.2.0 未发布”的默认集破坏性变更草稿。

- **选项 A（先 0.1.2 补丁线）**：只修发布 / 市场 / `doctor` / 文档契约，默认集暂不动（保持 41）；让 DSH 市场与 npm 先对齐到当前 10/41。代价：默认集不一致继续存在，P1 的“35 vs 41”决定要等下一版。
- **选项 B（直接 0.2.0）**：把默认集变更（按 D1 的选择）与发布 / 市场 / `doctor` 修复一起发。代价：破坏性变更与未验证的发布流程叠加，风险集中；需要更完整的迁移说明与回滚演练。

### D3. 工具级实测做到什么深度：全量还是端点 + 抽样？

**背景**：本次 9/39 有联网证据；探活只覆盖 8 个工具；全量 39 个工具实测会遇到限流（Strawberry 120 请求/分钟）、大响应（wheatomics 583 KB）与 ensemblplants 抖动。

- **选项 A（全量 39/39）**：每次（或每日）对 39 个源工具用固定参数实打一遍，判据“39/39 无未知”；覆盖最完整，成本与抖动最高，失败会频繁打断定时任务。
- **选项 B（端点 10/10 + 每周轮换抽检）**：每日只跑 10 个源级探活；每周轮换 10 个工具，30 天覆盖 39/39。判据“每周无未知项、30 天内覆盖 39/39”；成本低，但单个工具故障最晚 4 周才发现。
