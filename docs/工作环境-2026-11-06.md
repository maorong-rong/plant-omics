## ② 外网连通实测

**方法**：对同一 URL 各跑 5 次；成功 = `curl` 退出码 0 且 HTTP 2xx；`--max-time 20`。直连用 `--noproxy '*'` 明确绕过环境代理，代理用 `-x http://127.0.0.1:17891`。计时取 `curl` 的 `time_total`。

### 2.1 结果汇总

| 目标 | 路径 | 成功 / 次数 | 耗时（s，按 run 1–5） | 均值（s） | 退出码 |
|---|---|---|---|---|---|
| `api.github.com` | **直连**（`--noproxy '*'`） | **5 / 5** | 0.654 / 1.224 / 0.609 / 0.446 / 0.439 | 0.674 | 全 0 |
| `api.github.com` | **走 17891** | **5 / 5** | 1.261 / 0.487 / 0.482 / 0.462 / 0.467 | 0.632 | 全 0 |
| `github.com`（附加） | 直连（`--noproxy '*'`） | **0 / 5 完成** | 4 次 20 s 超时、1 次连接超时 | — | 全 28 |
| `github.com`（附加） | 走 17891 | **5 / 5** | 1.365 / 0.613 / 0.605 / 0.602 / 0.621 | 0.761 | 全 0 |

`api.github.com` 直连的 run 2（1.224 s）是单次抖动；代理 run 1（1.261 s）含首次建连/TLS 冷启动，之后稳定在 ~0.47 s。

### 2.2 失败原文（`github.com` 直连）

```text
run1 exit=28 [200 20.001200] stderr=[curl: (28) Operation timed out after 20001 milliseconds with 399256 bytes received ]
run2 exit=28 [200 20.000846] stderr=[curl: (28) Operation timed out after 20000 milliseconds with 512640 bytes received ]
run3 exit=28 [200 20.000664] stderr=[curl: (28) Operation timed out after 20000 milliseconds with 375544 bytes received ]
run4 exit=28 [200 19.999871] stderr=[curl: (28) Operation timed out after 20000 milliseconds with 445392 bytes received ]
run5 exit=28 [000 20.000632] stderr=[curl: (28) Connection timed out after 20000 milliseconds ]
```

注意：run 1–4 的 `http_code` 是 **200**，但正文在 20 s 内没传完（`exit=28`）。只看 HTTP 状态码会把「失败」误读成「成功」。

### 2.3 git 访问 GitHub（补充）

```text
$ git ls-remote origin HEAD
be2a505f562cb1b70084a3edfbf0d375a5f56d76	HEAD
exit=0 elapsed_ms=983                     # 默认：走 http.proxy=17891

$ git -c http.proxy= ls-remote origin HEAD
be2a505f562cb1b70084a3edfbf0d375a5f56d76	HEAD
exit=0 elapsed_ms=2419                    # 强制直连：能通，但慢约 2.5 倍
```

git 直连 `github.com` 能通（只拉协议引用，数据量小），而 `curl` 拉完整 HTML 会卡在正文传输。两者不矛盾。

### 2.4 结论：现在该走哪条

- **`api.github.com`：直连。** 5/5 成功、均值 0.674 s，与走代理（0.632 s）同一量级，且少一层对 17891 的依赖；代理首跑还多约 0.8 s 冷启动。
- **`github.com`：走 17891。** 直连 0/5 完成（4 次拿到 200 但正文传不完，1 次连不上），走代理 5/5、均值 0.761 s。
- 因此 issue 里说的现状「`github.com` 依赖 `127.0.0.1:17891`、`api.github.com` 直连」**现在仍然成立**，且 api 侧走直连是更稳的选择。
- 补充：git 的 `http.proxy` 只写在各仓库 `.git/config`，新 clone 默认直连；git 直连虽能通，但比走代理慢（0.98 s → 2.42 s）。

## ③ 我踩过的坑

### 坑 1：`ss` 在 WSL 里查不到 17891，差点误判代理已死

```console
$ ss -ltnp 2>/dev/null | grep 17891
$ echo $?
1
```

第一反应是「代理没在监听」。但同一时刻走代理请求是通的：

```console
$ curl -sS -x http://127.0.0.1:17891 -o /dev/null -w '%{http_code} %{time_total}\n' --max-time 20 https://api.github.com/
200 0.487
$ echo $?
0
```

原因：`.wslconfig` 是 `networkingMode=mirrored`，17891 是 **Windows 侧**的监听（`netstat.exe` 能看到 PID 10520），WSL 的 `ss` 只列 Linux 网络命名空间里的 socket。**教训**：健康检查代理要用 `curl -x`，不要用 `ss`。

### 坑 2：`curl` 返回 200 但退出码 28，只看状态码会假绿

```console
$ curl -sS --noproxy '*' -o /dev/null -w '%{http_code} %{time_total}\n' --max-time 20 https://github.com/ ; echo "exit=$?"
200 20.001200
exit=28
```

`http_code=200` 只代表响应头回来了，正文（几十万字节）在 20 s 内没传完。这正是 ② 里 `github.com` 直连 4/5「200 但失败」的原因。**教训**：脚本判定必须同时看退出码和是否收完，不能只看 `%{http_code}`。

### 坑 3：这台机器只有 `python3`，没有 `python`

```console
$ python --version
bash: line 1: python: command not found
$ echo $?
127
```

`sa-boot` 里用的是 `python3`，所以自启没受影响；但任何写死 `python` 的脚本会直接 exit 127。**教训**：脚本统一 `python3`。

### 坑 4（取证副作用）：找 autostart 的命令本身也会非 0

```console
$ grep -rn "sa-boot" ~/.bashrc ~/.profile ~/.bash_profile ~/.bash_login
grep: /home/maorongrong/.bash_profile: No such file or directory
grep: /home/maorongrong/.bash_login: No such file or directory
$ echo $?
2
```

退出码 2 是「文件不存在」，不是「没找到内容」（那是 1）。**教训**：报退出码时必须连上下文一起报，否则 1 和 2 会被混为一谈。

| 12 | 「不许改配置」与「实测」有张力：验证代理回退必须动 git 配置。 | 本次只能用 `git -c http.proxy=` 临时覆盖（不落盘）测直连；口径不清容易越界。 | 授权口径写明「允许临时、不落盘的验证参数（`-c`、`--noproxy`）」。 | `需要人做`（授权口径） |
| 13 | 「六类盘点 + 网络实验 + 异议」压成一个 issue。 | 报告长、验收项多，单次审查成本高，任一子项失败会拖住整体。 | 保持一个 issue，但验收按子项打勾、允许分批交付。 | `需要人做`（issue 模板） |

### 一句话总结

现状网络姿势成立：**`api.github.com` 直连、`github.com` 走 17891**；真正的风险不在「走哪条」，而在 17891 是 Windows 侧单点、git 代理配置不随新 clone 走、开机自启依赖用户登录且无自愈。
